## Correctness findings — before fixes

### F1 — P1: A same-path replacement repository inherits an old run's integration authority

**Locations:** [repository inspection](../../src/server/git/inspect.ts), lines 18–59; [repository schema](../../src/shared/domain/entities.ts), lines 35–41; [application identity check](../../src/server/orchestration/integration-apply.ts), lines 77–87; [recovery repository observation](../../src/server/orchestration/recovery-observe.ts), lines 36–69; [recovery decision](../../src/server/orchestration/recovery-decisions.ts), lines 217–233.

- **Trigger:** Prepare and approve a candidate, then replace the project directory with a separate clone at the identical canonical path. Keep the approved destination/result commits available and the destination at its recorded SHA. This can happen during a manual checkout restore/re-clone; it does not require racing the final Git command.
- **Cause:** Persisted repository identity consists of path strings, branch, SHA and cleanliness. Re-resolving the same root and common-directory paths does not establish that either directory is the original one. This differs from the explicit directory identity used for managed worktrees (`git/worktrees.ts:19–21, 296–303`) and adapter checkouts (`git/checkout-identity.ts:43–61`).
- **Consequence:** An approval bound to the original repository can mutate the replacement repository and be recorded as successful. Recovery also describes the replacement as verified, rather than requiring a repository-identity decision. This is a distinct failure of the documented replaced-checkout refusal, not the already documented lack of race-proof OS containment.
- **Executed evidence:** The disposable driver renamed the original checkout, then used local `git clone --no-local` to recreate its path. The `.git` inode changed from `1507150` to `1507482`. Recomputed application blockers were `[]`; confirming the previously displayed plan produced application `applied` and task `DONE`. The replacement branch advanced to the candidate while the original branch remained at the approved base. A second fixture reopened/recovered an unfinished attempt, made the same replacement, and observed `repository.state = verified`, prior worktree `inaccessible`; explicit acceptance of that *worktree* uncertainty allowed a new retry to become `QUEUED`. No native retry was launched in that second probe.
- **Confidence:** High; both effects asserted against real Git and SQLite. The probe demonstrates wrong-repository authority and mutation, not destruction of an unrelated history or uncommitted work.
- **Smallest proposed fix:** Persist and verify filesystem identity for the selected root and Git common directory, reusing the existing identity approach rather than adding a repository marker. Require explicit reopening/rebinding after replacement; legacy records without identity must not silently acquire authority from same-path existence. Enforce this in integration preparation/application and worker recovery/dispatch. Preserve old records/worktrees; do not repair or delete the replacement automatically.
- **Regression suggestion:** After approval, rename/re-clone at the same path with identical history and both approved commits present. Require refusal before an application claim/Git mutation and a non-verified recovery repository. Verify both repositories remain unchanged and accepting prior-worktree uncertainty cannot override failed repository identity.

### F2 — P1: A recovered reviewer can invalidate the verdict without invalidating the old approval

**Locations:** [review task creation](../../src/server/orchestration/review.ts), lines 61–71; [review assignment](../../src/server/storage/scheduling.ts), lines 130–135; [approval's in-flight statuses and review check](../../src/server/orchestration/integration.ts), lines 175–181 and 269–295; [durable review insertion](../../src/server/storage/reviews.ts), lines 87–115; [application eligibility](../../src/server/orchestration/integration-apply.ts), lines 31–59 and 240–245.

- **Trigger:** First review passes → prepare a passed preview → second review fails into `RETRY_DECISION` → approve the earlier preview → explicitly retry the second reviewer → its completed recommendation is `changes_requested` → apply the earlier approved preview.
- **Cause:** A failed review is not counted as in-flight at approval. Retrying the existing review task does not require its implementation to remain awaiting review. Inserting the new review preserves candidate approval, while final application eligibility checks neither the latest review ID/recommendation nor review execution in flight. Historical approval remains effective even though its reviewed evidence is no longer current.
- **Consequence:** A candidate with newer important findings can be integrated and marked `DONE` under an approval issued against the earlier passing assessment. The owner still clicks apply, but the backend does not demand a new preview/decision reflecting those findings; this defeats its existing stale-review gate.
- **Executed evidence:** Used the existing protocol-backed `reviewed()` fixture. A temporary SQLite `review.saved` trigger injected a review-journal failure, matching the existing rollback test; the second review reached `RETRY_DECISION`. Removed the trigger, approved the old preview, then used normal recheck/explicit recovery APIs to retry. Only the simulated review payload was replaced with existing `findingsReview`; gateway validation, clean checkout evidence, completion and persistence remained real. Durable recommendations became `[pass, changes_requested]`; the approved and newest review IDs differed. Application blockers were `[]`; the old preview applied, candidate became `integrated`, task became `DONE`.
- **Confidence:** High; full integration path reproduced with real Git/SQLite and simulated model output. A journal failure is one demonstrated route; delayed supervised reviews are another source-supported route, not separately executed here.
- **Smallest proposed fix:** Recheck exact review provenance in application eligibility and again in its claim transaction. Reject a newer review or an executing/requeued review of that candidate until a current passing preview is explicitly approved. Preserve immutable reviews and prior owner decisions as history; do not silently rewrite approval records. Define failed/deferred reviews explicitly rather than treating them as permanently irrelevant.
- **Regression suggestion:** Extend the existing failed-review rollback scenario through approval, explicit retry, new important findings and attempted apply. Assert no destination movement or application claim; require a current passing review and newly approved preview before integration. Include a retry already queued/running when apply is requested.

### F3 — P1: A persisted Chat/Plan change is not enforced after asynchronous safety checks

**Locations:** [integration application](../../src/server/orchestration/integration-apply.ts), lines 223–245 and 278–289; [native startup](../../src/server/orchestration/native-execute.ts), lines 116–157 and 204–212; [mode update](../../src/server/orchestration/engine.ts), lines 317–325. A related approval-only window exists in `orchestration/integration.ts:200–225`.

- **Trigger:** Start an application of an already approved preview, then switch the run to Chat/Plan while application planning awaits Git. Separately, switch to Chat/Plan while a worker's `startSession()` is awaiting initialization, before its first prompt.
- **Cause:** Application checks `run.mode` before awaiting `planApplication()`, not inside the subsequent claim transaction. The worker checks mode before `startSession()`, but its post-start guard checks only shutdown, pending stops and cancellation. A normal mode update changes none of those flags. These are ordinary event-loop interleavings, not external filesystem races.
- **Consequence:** Integration can begin and change the owner's destination after the stricter mode has committed. An initialized write-enabled worker can also receive its first prompt in Chat/Plan. This contradicts the current-owner-policy/no-mutation boundary and spec §4.2's requirement to apply mode changes before the next action.
- **Executed integration evidence:** Started `integrations.apply(...)` without awaiting, immediately called `engine.updateRun({id, mode: "chat_plan"}, ...)`, then awaited application. The mode update was journal sequence **65**, application start **67**. Mode remained `chat_plan`; application was `applied`, destination advanced, task was `DONE`.
- **Executed startup evidence:** A gated `FakeAdapter` subclass held `startSession()` for a directly reserved disposable native writer attempt. After changing mode, releasing startup produced **one first prompt** in `chat_plan`; the prior worktree was retained. No actual harness/process/model was invoked by this probe. It proves the engine's dispatch boundary, not native file edits.
- **Confidence:** High for the two executed paths. The approval-only await window and adapter-internal timing after prompt dispatch are not independently exercised here.
- **Smallest proposed fix:** Re-read current mode at the integration decision/application transaction and immediately before native prompt submission after startup. Recheck shutdown at the same claim boundary. Use the existing refusal/interrupted cleanup paths; never roll back Git or discard the initialized checkout. Do not redefine a scheduling pause as cancellation of already running work.
- **Regression suggestion:** Deterministically interleave a mode change during application planning and gated worker initialization. Require no application claim/destination movement and no first worker prompt, respectively; verify retained evidence and normal explicit recovery. The application assertion must check event order, not merely switch mode before invoking apply.

## Coverage gaps and unresolved questions — not additional demonstrated bugs

- **Failure timing matters:** `tests/integration-apply.test.ts:343–370` manually commits a claim and finishes Git, then closes the app; it does not kill the app while Git is alive or partially updating a checkout. A surviving Git child after app death, interruption during checkout/index/ref changes, and a competing owner recovery decision remain unexecuted scenarios. Add gated disposable subprocess cuts before/after each external operation; retain the conservative decision barrier.
- `tests/restart-reconciliation.test.ts:93–162` constructs busy persistent state plus a real `sleep` survivor. It proves observation/no-signalling behavior, not the exact native executor spawn-to-session-record cut. `tests/runtime-faults.test.ts:259–290` restarts after `engine.idle()` has finalized the failure. `tests/worktrees.test.ts:140–150` changes a completed creation record back to `creating`, rather than interrupting the original Git operation.
- **Spawn/completion cuts:** A native process can exist before its returned PID/session metadata is persisted; no orphan mutation was demonstrated. Candidate refs and report files can exist before final SQLite completion. Existing candidate/review rollback tests cover useful specific cuts, not every ordering of filesystem, journal, transaction and release. Determine how all retained-but-unregistered evidence is presented before claiming exhaustive recovery.
- **Multiple app processes:** Startup protects against an occupied chosen port, not a proven exclusive database lease across different ports. Simultaneous app instances sharing a database were not executed. Determine whether that deployment is rejected/documented; do not infer singleton ownership from SQLite write serialization.
- **Recovery evidence freshness:** `recovery-decisions.ts:188–195` compares repository/worktree/process classifications, not every Git/session/tool field shown to the owner. The [restart ADR](../adr/2026-10-16-restart-reconciliation.md), lines 16–23, explicitly makes those extra fields evidence-only because retry uses a new checkout/session. This is an intentional tradeoff, not a newly discovered stale-approval bug; an owner may still benefit from a clearer evidence timestamp/change warning.
- **Known residual Git race:** The [application ADR](../adr/2026-10-16-integration-apply.md), line 16, already records the external branch-switch window between final checkout observation and `git merge`. No new distinct failure was demonstrated there. OS containment, descendant termination, executable-filter refusal, unsupported resume and incomplete live harness parity remain documented limitations, not new findings.
- No fresh browser interaction, native harness compatibility/model call, power-loss/filesystem durability test, exhaustive adversarial interleaving search or owner-data recovery was performed. Default tests and API/protocol smoke are not substitutes for these. No lost-work or duplicate-replay claim is made for unexecuted scenarios.

## Product/architecture assumptions — proposals, not correctness findings

The local single-process/SQLite/native-harness design remains a reasonable fit for the one-owner goal. These experiments test friction/complexity without authorizing a rewrite, OS-safety claim, native spend or managed-repository mutation. Settled authority/workflow changes require spec §17 review and an ADR before implementation.

| Assumption to challenge | Simpler alternative and tradeoff | Small reversible experiment |
| --- | --- | --- |
| Preview approval and final apply confirmation both need separate persistent owner actions (`integration-panel.tsx:312–374`, `apply-panel.tsx:62–85`). | One final owner decision could bind the exact preview, current apply plan, tests and destination in a single claim. Fewer stale-state windows/clicks, but owner loses the useful “approved, apply later” state. Never infer approval or remove final Git rechecks. | Compare the current UI with a static/fixture-only combined confirmation showing the same evidence and refusal states. Measure missed target changes and number of interventions; do not connect it to a mutating endpoint. Keep current behavior unless the owner chooses the tradeoff. |
| Any dirty or moved root should stop useful isolated work (`engine.ts:425–439`, `git/worktrees.ts:61–73`). | A selected immutable commit could support read-only exploration without requiring the owner's current checkout to stay pristine. This separates snapshot identity from mutable checkout state, but adds snapshot selection/provenance and risks stale answers. Writers/integration must retain their existing refusals until separately designed. | On disposable fixtures, compare current refusal with a read-only snapshot-only route while the root is dirty/moved; assert byte-for-byte owner-tree preservation and prominent snapshot SHA. Collect whether real owner-selected exploration benefits before proposing a mode/config option. |
| Several related ledgers/status families are needed to explain every recovery (`attempt`, `dispatch`, reservation, worktree, preview/application, manual request). | Keep existing durable records, but present one operation timeline derived from them; avoid adding another mutable “recovery manager” state. A single operation ledger might eventually be simpler internally, but migrating everything now would risk exactly-once/retention invariants without demonstrated benefit. | Write a fixture-only cut-point matrix that maps every external mutation to its before/after durable records and owner action. Replay current recovery scenarios into that view. Count contradictions/missing evidence before considering any schema consolidation. No queue/service/framework or distributed transaction layer is justified. |
| A fresh retry with a checkpoint is the right default even when retained partial work looks useful. | Preserve that safe default; optionally let the owner select existing immutable candidate/report evidence for a fresh attempt instead of manually reconstructing a handoff. Do not resume an ambiguous process or adopt its writable checkout. Selection reduces lost effort but adds another provenance decision and context cost. | Run a no-cost fixture drill with a retained partial change: compare the current fresh checkpoint with an explicitly selected immutable evidence packet. Verify different worktree/session IDs, unchanged prior work and no automatic replay; measure whether the manual effort actually decreases. |
