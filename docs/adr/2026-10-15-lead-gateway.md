# M4 Codex Lead and session-scoped tool gateway

## Context

M4 needs a live Lead that can coordinate workers only through validated engine operations. Installed Codex 0.162.1 `app-server` (stdio JSON-RPC; not `exec-server`, which the owner's desktop app uses for cloud environments) accepts per-thread `config.mcp_servers` with a bearer token read from an environment variable; `dynamicTools` exists only behind the experimental API. Pi 1.3.0 connects extension-registered MCP servers through its built-in `builtin:mcp` extension. Codex writes several SQLite stores into `CODEX_HOME` even without a model turn, and an app-owned home starts unauthenticated.

## Decision

- **One stateless Streamable-HTTP MCP endpoint** (`POST /mcp`) on the existing loopback server, with no SDK dependency. Each Lead/worker session gets a random bearer token; only its SHA-256 digest is held in memory, bound to session, role, run, task and attempt, and revoked when the turn ends (restart revokes all). Tools are listed per role and per current mode; every call is re-authorized through `engine.tool()` (session liveness, role, run scope, mode allowlist, ownership, owner pins, budgets) and journaled. Denials return structured `isError` results.
- **Codex Lead** runs one app-server process per Lead turn with an app-owned `CODEX_HOME` (`<app data>/codex`), verified from the `initialize` response. Owner authentication stays native: the owner runs `CODEX_HOME=<that path> codex login`; credentials are never copied. Threads use `sandbox: read-only` (no network) and `approvalPolicy: never`, checked in the `thread/start`/`thread/resume` response before any prompt; approval requests that still arrive are declined. Startup also requires the `lao` MCP server to be connected. The first live run showed Codex refuses non-read-only MCP tools under `never` ("MCP tool call requires approval"), so only the `lao` server sets `default_tools_approval_mode = "approve"`; the gateway, not a harness prompt, is the authority for those calls.
- **Native delegation is blocked where the harness exposes it**: multi-agent, apps, plugins, hooks, worktrees, memories, browser/computer use, image generation and web search are disabled and verified via `experimentalFeature/list`; reasoning efforts whose native description says they delegate are not offered; any `collabAgentToolCall`/`subAgentActivity` item interrupts the turn.
- **Serialized wake-ups**: each Lead turn is a lead task through the existing scheduler, whose one-Lead-reservation-per-run index prevents concurrent prompts. Worker completion, failure and high/urgent issues request a turn; a queued turn absorbs later inputs. Automatic turns count against `maxAutomaticLeadWakeupsPerRun`; owner messages do not. Each turn resumes the run's Codex thread and receives a digest of journal events since a durable delivery cursor, including owner overrides.
- **Supervised** Lead assignments/revisions become owner-approval proposals; the scheduler still refuses Lead dispatch outside Autonomous mode. Revisions create child tasks (bounded by `maxRevisionCyclesPerTask`); Lead assignment checks queued + launched work against the launch budget.
- **Pi workers** get `--extension builtin:mcp`, `--tools …,mcp__lao__*` and the guard registers only the `lao` server; the guard allows only the four worker gateway tools without path checks. Text-only results remain survivable but are labeled unverified.

## Consequences

The Lead can read the owner's checkout through its sandboxed shell (reads are not confined to the repository), but cannot write it, reach loopback services or start networked processes; a before/after HEAD+status check pauses the run if the checkout changes during a Lead turn. Live steering, blocking human-request suspension, answer controls and resume of interrupted Lead turns remain M6. MCP role separation is a guardrail, not hostile-code isolation.
