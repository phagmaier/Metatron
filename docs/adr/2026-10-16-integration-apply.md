# M5: confirmed application of an approved integration

## Context

Spec §8.6.4–6: the owner sees the target branch/SHA and proposed Git commands and explicitly approves applying the result; immediately before application the engine rechecks the branch, its SHA and cleanliness, fails safely if anything moved or is dirty, and never overwrites or resets local changes. Integration commit IDs and an audit trail persist. Spec §10 forbids automatically rerunning ambiguous mutating work.

## Decision

- **Plan, then confirm exactly that plan.** `GET /api/integrations/plan` is read-only and recomputed on every request. It checks repository identity, that `refs/heads/<destination>` is still at the approved preview's destination SHA, and that the result commit exists and fast-forwards it. It also finds where the branch is in use. Plans with **blockers** cannot be confirmed: the branch is checked out in another worktree, a rebase or bisect in any owner worktree holds it (a bare `update-ref` would move it underneath), the owner's checkout is on the branch and dirty (tracked, staged or untracked) or mid-operation, or the branch moved. The plan names one method and its exact argv: `update_ref` (`git update-ref <ref> <result> <approved SHA>`, a compare-and-swap) when the branch is not checked out; `fast_forward_checkout` (`git merge --ff-only --no-autostash --no-overwrite-ignore --no-verify-signatures`, submodule recursion off) in the owner's clean checkout when it is; `record_existing` (no command) when the branch already points at the result. `POST /api/integrations/apply` carries the confirmed method, SHAs and checkout path. The server recomputes the plan and refuses any difference or blocker, so nothing changes.
- **Claim before Git, verify after.** The claim transaction appends an `applying` record to the preview and moves the lineage to `INTEGRATING`. Only then does Git run, after one more check of the checkout's branch, HEAD and cleanliness right before the fast-forward. The outcome is read from Git afterwards, not from the exit code: at the result → `applied`, lineage `DONE`, candidate `integrated`; verifiably unchanged after a refusal (or nothing ran) → `blocked`; anything else → `interrupted`, with a high-urgency "Needs you" request. Both of the last two move the lineage to `BLOCKED_CONFLICT`. A request replayed with the same idempotency key returns the record and never runs Git again.
- **Recovery never reruns.** At startup an `applying` record becomes `interrupted` (Git not rechecked) with the same request. Applying again from `BLOCKED_CONFLICT` goes through a new plan (`BLOCKED_CONFLICT → READY_TO_INTEGRATE → INTEGRATING`). If Git had already reached the result, the plan offers `record_existing`.
- **Reconciling a moved destination.** While `READY_TO_INTEGRATE` or `BLOCKED_CONFLICT`, the approved candidate may get a new preview, which the owner approves (no decline at that stage). Only the latest approved preview can be applied. Shutdown waits for an application in progress instead of aborting it; owner-only, refused in Chat/Plan.

## Consequences

The owner's branch changes only by a confirmed fast-forward or compare-and-swap, and their dirty checkout, local and ignored files are never overwritten, stashed or reset. Residual risk: between the last check and `git merge`, an owner who switches branches could have that branch fast-forwarded if it is an ancestor of the result. Verification then reports `interrupted` instead of claiming success. A conflicting preview still leaves task state unchanged; only applications use `BLOCKED_CONFLICT`. App-owned worktrees and branches are kept after success; cleanup is not implemented. No dependency, toolchain, migration or spec change; earlier preview records read with no applications.
