# M8 item 5: read-only Codex workers and natively confirmed settings

## Context

M8 item 5 requires all four harnesses to act as read-only workers with their selected model and thinking level actually applied. Through item 4, Codex was Lead-only: the adapter refused anything but a gateway-connected `coordinator`, and profiles, teams, native runs and worktree preparation excluded it. Codex has no separate file-read tool; it reads through its shell, which installed 0.163.0 runs in its own read-only sandbox without network (bwrap on this machine, verified for the M4 Lead). The other three harnesses read through app-guarded file tools that refuse sensitive paths. A no-model probe of installed Codex 0.163.0 showed `thread/start` with `config.model_reasoning_effort` reports that effort back as `reasoningEffort` (`null` when unset), and the protocol defines `model/rerouted` (reason `highRiskCyberActivity`), which the event mapper previously ignored. Before this item, adapters checked model/thinking (Pi `get_state`, Claude init plus native effort report, OpenCode step model/variant), but nothing durable recorded the result.

## Decision

- **Codex may be a `read_only` worker, never a writer.** The adapter accepts a fresh, gateway-connected read-only thread or a coordinator Lead, and nothing else; worker threads are never resumed (each assignment owns a new worktree, as for Pi). It reuses the Lead's checks: app-owned `CODEX_HOME`, all 14 delegation/side-channel features reported disabled, `sandbox: readOnly` with no network, `approvalPolicy: never`, the `lao` MCP server connected (probing `read_assignment` for workers), and declined approval requests. Profiles, teams, owner-directed native runs and worktree preparation admit Codex only with `read_only`; the engine also refuses a Codex non-reader before launch.
- **Effort is applied at thread start and verified from the response.** A requested effort is sent as `config.model_reasoning_effort`, and prompts are refused unless the response reports that exact model and `reasoningEffort`. This also applies to the Lead.
- **A model reroute fails the turn.** `model/rerouted` (like native delegation) interrupts the turn, and a turn that completes before the interrupt lands is mapped to `failed`, so it is never treated as success.
- **Every adapter journals `<harness>.settings_verified`** immediately before a completed turn, with the model and thinking level the harness confirmed and which native signal confirmed them. Claude reports the native model id it resolved, for example `haiku` → `claude-haiku-5-5`.

## Consequences

A Codex reader cannot write the checkout and has no network, but **its reads are not confined to the worktree**: it can read any file the owner's user can, including paths the other workers' guards refuse. This matches the existing Lead and is stated in discovery, profile diagnostics and the README. It is not an OS isolation boundary and makes no secret-path guarantee. Restricting Codex reads (for example through permission profiles) is not attempted in beta. Worktree evidence still carries the historical `tests: "not_run: shell tools are disabled in M3"` literal, which is inaccurate for Codex readers; that persisted schema is unchanged. `settings_verified` confirms what the harness applied, not entitlement or price, and a request equal to the model's native default proves application, not that the request changed anything.
